# 분석 결과 뷰어 (UI) 설계

작성일 2026-11-19. 상태: 사용자 승인 대기.

## 의도와 이유

vb_trk는 중계 영상을 넣으면 선수·팀·이벤트·공·랠리를 뽑아 CSV·그림으로 내는 오프라인 파이프라인이다.
사용자의 최종 목표는 **전략분석 프로그램**이고, 그 첫 단계로 "실제로 실행되는 UI가 있는 프로그램"을 원한다.
이 문서의 범위는 그중 **이미 만들어진 분석 결과를 보는 화면**이다. 분석은 따로(몇 시간, 명령줄로) 돌리고, UI는 결과만 본다. 실시간은 필요 없다 (사용자 확인).

쓰는 사람과 정확한 사용 장면은 사용자가 아직 구체적으로 말하지 않았다. 사용자가 고른 것은 "한 점씩 복기" 화면(B)을 첫 화면으로, "경기 전체 통계"(C)를 탭으로 전환하는 구성이다.

## 목표

- `python app.py` 한 줄로 서버가 뜨고 브라우저에서 화면이 열린다. 인터넷 없이 동작한다.
- **복기 탭 (첫 화면):** 랠리 목록 → 하나를 고르면 그 랠리 구간의 영상이 재생되고, 영상 위에 선수 박스(팀 색)·공 위치/꼬리·이벤트 글자가 겹쳐 그려지며, 옆에 코트 지도(선수 위치, 접촉 위치를 순서대로 연결)가 같이 움직인다.
- **경기 통계 탭:** 득점, 서브 득점률, 사이드아웃률 카드 + 기존 분석 그림(`<영상>_analysis.png`)을 보여 준다.
- 경기(영상)가 여러 개 있으면 상단에서 고른다 (`outputs/`에서 자동으로 찾는다).
- 분석 결과의 **불확실성을 숨기지 않는다**: 득점 팀 판정 약 85%, 랠리 시작·득점은 추정이라는 안내를 화면에 상시 표시하고, 코트를 못 잡은 구간(박스가 비는 구간)은 "이 구간은 코트 인식 실패"로 표시한다.

## 비목표 (이번에 안 함)

- UI에서 분석을 실행하는 것 (명령줄 파이프라인이 그대로 한다).
- 실시간 처리, 여러 사용자, 로그인, 라벨 수정·메모 같은 편집 기능, 모바일 대응.
- 디자인 다듬기. 이번엔 구조·동작이 목표이고, 외형(DESIGN.md 등)은 다음 단계다. 단 색·간격은 한 곳(CSS 변수)에 모아 나중에 바꾸기 쉽게 한다.
- 대각선 앵글 코트 인식, 공 바운드 (사용자가 하지 않기로 함).
- 설치형 `.exe` 패키징 (나중 작업).

## 안티 목표 (기술적으로 돼도 실패인 것)

- 방송 화면이 들어간 파일을 저장소에 커밋하는 것 (영상·캡처·GIF는 git에 안 들어간다. `.gitignore`).
- 분석 결과가 정확한 것처럼 보이게 하는 것.
- 영상과 박스가 어긋나 보이는 것 (동기화가 틀리면 도구로 쓸 수 없다).
- 런타임에 외부 CDN·서버에 의존하는 것.

## 제약

- 저장소 라이선스는 AGPL-3.0, 비공개 저장소. 영상 파일은 DVC 포인터만 있고 `data/`에 로컬로 존재한다.
- Windows, Python은 anaconda base. 파일 읽기·쓰기는 항상 `encoding="utf-8"` (기본 cp949 때문에 깨진 적 있음).
- 기존 분석 산출물 형식을 바꾸지 않는다. UI는 `outputs/<영상>_{rallies,events,tracks,ball,players}.csv`와 `_analysis.png`를 **읽기만** 한다.
- 영상: 방송 3개는 1920×1080 VP9 mp4(최대 1.1GB, 약 30fps 29.97)로 브라우저가 재생한다. 데이터셋 클립(`long_20` 등)은 MPEG-4 Part 2(FMP4)라 브라우저가 못 읽는다 → 한 번 H.264로 변환해 캐시한다.
- 큰 파일이라 영상은 HTTP Range 요청(구간 이동)을 지원해야 한다.
- 추적 CSV는 1세트만 15만 행이므로 한꺼번에 보내지 않고 랠리 구간만 잘라서 보낸다.

## 데이터 (UI가 읽는 것)

| 파일 | 열 | 쓰임 |
|---|---|---|
| `_rallies.csv` | start(프레임), serve_team, winner, contacts, seconds | 랠리 목록, 영상 구간 (끝 = start + seconds×fps) |
| `_events.csv` | start, end, peak, group, team, action, conf, actor, court_x, court_y | 영상 위 이벤트 글자, 코트 지도의 접촉 위치 |
| `_tracks.csv` | frame, track_id, team, x1,y1,x2,y2 (영상 픽셀), court_x, court_y (미터), airborne | 선수 박스, 코트 지도 |
| `_ball.csv` | frame, x, y (영상 픽셀), score | 공 위치·꼬리 |
| `_players.csv` | 트랙별 이동 거리·속도 | (이번 범위에서는 안 씀) |

공 위치는 영상 픽셀뿐이고 코트 좌표(미터)가 없다. 그래서 코트 지도에는 공 궤적 대신 **접촉 위치(이벤트의 court_x/y)를 시간 순서로 연결한 선**을 그린다. (시안의 "코트 위 공 궤적"에서 바뀐 부분)

## 접근 방식 (검토한 것)

1. **로컬 웹 앱 (선택)**: Python(FastAPI) 서버 + 순수 HTML/JS. 영상 재생 시각에 맞춰 canvas에 박스를 겹쳐 그림. 영상 시크, 탭, 표, 그림이 모두 자연스럽고 저장소에서 받아 한 줄로 실행.
2. 데스크톱 앱(PySide6): 진짜 창이지만 설치가 무겁고 표·탭·그래프 화면 꾸미기 비용이 큼.
3. Streamlit: 가장 빠르지만 재생 시각과 동기화된 겹쳐 그리기가 안 돼 복기 화면의 핵심을 못 살림.

사용자가 1번을 골랐다 (이유: B와 C를 모두 살리는 데 가장 맞음).

## 설계 (제 판단으로 정한 것은 "내 판단" 표시)

- **구성:** `app.py`(서버 진입점, `python app.py [--outputs outputs] [--data data] [--port 8000]`), `ui/` 폴더에 `index.html`, `app.js`, `style.css`(프레임워크·빌드 단계·CDN 없음, 내 판단). 서버는 `serve.py`와 별개 (그쪽은 모델 서빙).
- **API (읽기 전용):**
  - `GET /api/matches` → 영상 이름 목록, 각각 fps·프레임 수·해상도·영상 파일 유무
  - `GET /api/matches/{stem}/rallies`, `/events`, `/summary`(득점·서브 득점률·사이드아웃률), `/figure`(분석 PNG)
  - `GET /api/matches/{stem}/frames?start=&end=` → 그 구간의 선수 박스·공 위치 (컴팩트 배열)
  - `GET /video/{stem}` → Range 지원, 필요하면 H.264 변환본
- **동기화:** 브라우저의 프레임 단위 콜백으로 재생 시각 → 프레임 번호(`시간×fps`)를 구해 그 프레임의 박스를 그린다. 구간 이동 시 랠리 구간 데이터를 미리 받아 둔다.
- **복기 탭:** 좌측 랠리 목록(번호, 시각, 서브 팀 → 득점 팀, 접촉 수, 길이), 우측 위에 영상+겹침, 우측 아래에 코트 지도와 랠리 요약. 방향키로 이전/다음 랠리.
- **통계 탭:** 요약 카드 + 분석 그림. 숫자는 `_rallies.csv`에서 서버가 계산 (내 판단: 처음엔 새 그래프를 안 만들고 기존 PNG를 재사용).
- **불확실성 표시:** 화면 상단에 "득점 팀 판정 약 85%" 문구, 랠리 목록에 근거 부족 표시, 박스가 없는 프레임 구간 안내.
- **영상 변환 (내 판단):** 서버 시작 시 코덱을 검사하고 브라우저가 못 읽는 영상은 `ui_cache/`에 H.264로 한 번만 변환 (imageio_ffmpeg가 이미 설치돼 있음). 변환 중엔 화면에 안내.
- **오류 처리:** 영상은 있는데 결과가 없거나 반대인 경우, 결과 일부 CSV만 있는 경우를 화면 문구로 알려 준다.

## 세부 결정 (빌더 검토 반영, 모두 내 판단)

- **경기 찾기:** `outputs/<이름>_rallies.csv`가 있고 **행이 1개 이상**인 이름만 경기로 나열한다 (`match1_set1/2/3`). 데이터셋 클립(`clip_*`, `long_*`)은 랠리가 없어 목록에 안 나온다. 영상은 `data/<이름>.mp4`로 고정 (현재 세 개 모두 있음). 영상이 없으면 "결과만 있음, 영상 없음" 표시로 통계 탭은 열린다.
- **fps·프레임 번호:** fps는 영상 파일에서 읽는다 (29.97003 같은 실제 값, 30으로 가정하지 않는다). 영상이 없으면 29.97. CSV의 `frame`·`start`·`end`·`peak`은 모두 같은 번호(0부터 읽은 순서)다. 재생 시각 × fps로 프레임을 구하고, 이 값이 틀리면 박스가 밀려 보이므로 동기화 확인(검증 2)을 통과해야 한다.
- **팀 표기·방향:** 팀은 `LEFT`/`RIGHT` (화면 기준 왼쪽·오른쪽 코트). LEFT=빨강, RIGHT=파랑 (기존 분석 그림과 같다). 코트 지도는 가로축 = `court_y`(0~18 m, 길이 방향), 세로축 = `court_x`(0~9 m)로 그리고, `court_y`가 작은 쪽이 LEFT다 (1세트 선수 위치 중앙값: LEFT 5.9, RIGHT 12.0으로 확인). `FAR`/`NEAR` 표기는 옛 데이터셋 클립 결과에만 있고 이 UI 범위 밖이다.
- **랠리 구간·이벤트:** 재생 구간은 `start − 2초` ~ `start + seconds + 2초`(영상 범위로 자름). 랠리에 속하는 이벤트는 `start ≤ event.start < 랠리 끝`이고 득점(winpoint)은 제외 (`analysis.py`의 접촉 수 정의와 같다).
- **득점 팀은 추정:** `winner`는 따로 관측한 값이 아니라 "다음 랠리의 서브 팀"이다 (`analysis.rallies`). 마지막 랠리는 `winner` 없음으로 표시한다. 이 때문에 득점 팀 판정 약 85% 문구를 상시 표시한다.
- **"근거 부족" 표시 규칙:** 랠리 접촉 수가 2 이하, 또는 길이 5초 미만, 또는 `winner` 없음이면 주의 표시. (CSV에 확신도 열이 없어서 이 세 조건만 쓴다.)
- **"코트 인식 실패" 표시 규칙:** 재생 구간 안에서 선수 박스가 **연속 30프레임(약 1초) 이상 없는** 구간을 타임라인에 회색으로 표시하고 "이 구간은 코트 인식 실패(클로즈업·리플레이 등)"로 안내한다. 그보다 짧은 끊김은 무시.
- **통계 정의 (`analysis.py`와 같게):** 득점 = 팀별 랠리 승수 (`winner` 없는 행 제외). 서브 득점률 = 그 팀이 서브한 랠리 중 이긴 비율. 사이드아웃률 = 그 팀이 리시브한 랠리(상대가 서브) 중 이긴 비율. 팀별로 따로 보여 준다.
- **공 데이터:** `x`·`y`가 빈 행은 "공 없음"으로 건너뛴다 (0으로 취급하지 않는다).
- **의존성·지원 범위:** FastAPI·uvicorn은 이미 설치돼 있다 (서빙 서버에서 사용). CI용 `requirements-ci.txt`에 FastAPI·uvicorn·httpx를 추가한다. VP9를 재생 못 하는 브라우저는 범위 밖 (Chrome·Edge 기준).

## 검증 (이게 되면 완성)

1. 서버 API 테스트(pytest): 합성한 작은 CSV 한 벌로 각 엔드포인트의 형태, 구간 자르기 경계, 없는 영상 이름의 404, Range 응답(206).
2. 실제 데이터 수동 확인: 1세트에서 랠리를 골라 재생했을 때 선수 박스가 영상 속 사람과 맞는지, 공이 맞는지를 캡처로 확인 (**동기화가 안티 목표라서 가장 중요**).
3. CI(GitHub Actions)에 API 테스트 추가. 실제 영상이 없으니 합성 데이터로.

## 빌더에게 남기는 것

- 프론트 코드 세부(파일 분할, 함수 구조), 색·간격 값, 목록 정렬·키보드 단축키 세부.
- 영상 변환 옵션(품질·속도), Range 응답을 직접 구현할지 프레임워크 기능을 쓸지.
- 한 경기당 구간 데이터의 보내는 형식(컴팩트 배열 구조)과 크기 상한.
